# 项目范围与研究问题

## 1. 背景

传统 Web 扫描器擅长规则化、单请求和无状态检测，但在前后端分离、多身份、多页面、多接口联动和业务状态依赖明显的场景中容易出现覆盖不足与误报。大语言模型具备语义理解和任务拆解能力，但单模型在长链路任务中容易丢失上下文、重复执行或用自然语言主观下结论。

AgentGo 的研究重点不是简单把 LLM 接到扫描器上，而是验证以下组合能否提升授权 Web 测试的完整性、稳定性和可解释性：

- 多 Agent 职责拆分；
- 页面、接口、参数、身份、请求、响应统一上下文；
- 带来源和安全约束的知识检索；
- 非破坏主动验证；
- 独立复核和证据化结论。

## 2. 研究问题

RQ1：Multi-Agent 相比单 Agent，能否提高长链路测试任务完成率并减少重复或偏航？

RQ2：KnowledgeAgent 和结构化 KnowledgePack 能否提高测试策略的适用性并减少无关请求？

RQ3：独立 Verifier 和版本化确认规则能否降低误报率？

RQ4：在永久禁止破坏性动作的情况下，低影响主动探测能否形成足够强的漏洞证据？

RQ5：统一上下文和检查点能否提升多身份、跨页面和多请求业务场景的可恢复性？

## 3. 使用者与场景

- 高校网络安全教学与靶场实验；
- 项目组的授权研究和竞赛训练；
- 中小研发团队对自有系统的上线前自查；
- Multi-Agent 安全测试方法研究。

## 4. V1 支持矩阵

| 漏洞族 | 研究重点 | 确认证据 | 不做的动作 |
|---|---|---|---|
| SQL 注入 | 参数语义、基线/布尔/时间/错误差异 | 可重复差异、负对照、请求响应摘要 | 数据写入、结构修改、堆叠破坏语句 |
| XSS | 反射位置、编码上下文、DOM sink | 隔离浏览器中的惰性标记执行证据 | Cookie 外传、真实用户触发、持久恶意内容 |
| SSRF | URL 参数、服务端访问行为、重定向边界 | 受控回连或授权测试服务访问记录 | 云元数据、未授权内网、回环与越界地址 |
| 越权 / IDOR | 身份、资源归属、接口差异 | 两个授权身份下的只读访问对照 | 修改、删除、公开真实用户数据 |

V1 必须让四类漏洞都能走通 Signal -> Validation -> Verdict -> Report，而不是只完成 UI 或通用 Agent 框架。

### 4.1 V2 完整 Web 分类目标

V1 四类仍是已经实现的研究基线，不是项目长期上限。V2 采用开放式 Family/Technique DefinitionRegistry 与独立 ActivationCatalog，把 WSTG、ASVS、API Security Top 10 和授权 SRC 场景纳入覆盖目录，包括配置/泄漏、认证/会话/授权、各类注入、文件/XML/服务器解析、客户端、REST/GraphQL/WebSocket、业务逻辑/竞态、协议/缓存、组件情报和 LLM Web。注册只说明定义完整，不能替代评测资格或主动执行授权。

“纳入”必须有明确状态：`active-l1`、`active-l2`、`signal-only`、`fixture-only`、`inventory-only` 或 `forbidden`。项目不承诺自动发现所有未知漏洞，也不通过高风险利用证明追求表面覆盖；无法在真实业务中安全确认的类别保持 Signal、Inconclusive 或专用 fixture。

近期工作先交付通用后端和四个参考主动模块，再按共享能力逐类完成模块交付定义。当前前端仅维持可构建、可启动和既有流程可用，后端合同稳定后再统一重建。

## 5. 主动探测定位

主动探测不是可选装饰，而是形成明确结论的必要能力。系统默认允许范围内、低影响、非破坏的 L1 主动探测；对需要创建临时测试对象、受控上传或回连的 L2 动作要求人工确认、专用测试数据和清理记录；L3 破坏性动作永久拒绝。

主动探测的目标是验证假设并收集证据，不是扩大影响。证据充分后立即停止，不继续追求更高权限或更大数据量。

## 6. 非目标

- 未授权公网资产扫描；
- 高并发分布式扫描平台；
- 自动化红队全链路；
- 生产数据增删改、持久化、横向移动、凭据喷洒；
- 高强度 DoS、WAF 规避和隐蔽执行；
- 自训练基础大模型；
- V1 中建设通用 Kali 控制平台或大型图数据库。

## 7. 交付物

- 可安装或可运行的 Windows 桌面原型；
- 核心五 Agent 和确定性执行/安全服务；
- 四类漏洞的知识条目、确认规则和评测用例；
- 固定版本靶场上的基准、对照和消融结果；
- 结构化 Findings、证据包和修复建议；
- 项目研究总结、使用说明和软件著作权申报材料。

V2 增量交付还必须包含：

- 版本化 Vulnerability DefinitionRegistry/ActivationCatalog、通用 Subject/ValidationPlan/Capability 和角色化 Evidence；
- 完整 Web 漏洞覆盖矩阵及每项真实成熟度；
- 每个 Active Technique 的 Detector、确认规则、修复建议、正负/Inconclusive/安全 Case；
- 20 天后的七波纯后端覆盖路线和后端稳定后的前端重建输入合同。

## 8. 成功定义

项目成功不仅意味着“软件能够启动”，还必须满足：

- 授权范围外请求为 0；
- 破坏性动作执行数为 0；
- 每条 Confirmed Finding 都有确认规则、复现步骤和证据引用；
- 四类 V1 漏洞都有正例、负例和误报分析；
- 能报告 Precision、Recall、F1、误报率、任务完成率、运行成本和稳定性；
- 能通过对照实验解释 Multi-Agent、KnowledgeAgent 和 Verifier 各自带来的价值。
